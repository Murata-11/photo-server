# DB設計（レビュー案）

状態：未承認・未実装。2026-11-10のチャットによるDBML + dbdiagram.ioでの設計依頼に基づく。スキーマの正は [db/schema.dbml](../db/schema.dbml)。本書は設計意図とDB外の整合性ルールを説明する。

## 対象と関連

| テーブル | 役割 | 関連 |
| --- | --- | --- |
| app_users | 許可する2人と信頼する入口の安定IDの対応 | 1人が複数の写真を追加 |
| photos | 元ファイルの保存キー、検証済み形式、サイズ、追加日時 | 全写真が共通領域に属する |
| photo_metadata | 撮影現地日時・既知のUTCオフセット・GPS・解析状態 | 写真ごとに1行 |
| photo_thumbnails | 再生成可能なサムネイルの保存キーと生成状態 | 写真ごとに1行 |

アルバム、タグ、地名、公開リンク、利用者別権限、検索APIは追加しない。写真のバイナリをDBへ格納せず、DBと永続ファイル領域を整合した単位でバックアップする。

## 型とDB製品

DBMLはPostgreSQL向けの型で具体化した設計案。製品の採用・運用構成を確定するADRではなく、実DBやマイグレーションは作成しない。SQLiteなどを選ぶ場合は日時・数値・Enum・制約を変換して再検証する。

UUIDはサーバーが発行する。追加・解析・生成・削除時刻は時点を表す型を使い、出力はUTCとする。撮影現地日時はタイムゾーンなしで保存し、未知のオフセットを補完しない。PostgreSQL timestampの小数秒上限を超えるEXIFの桁は、選定・実装時に別の文字列表現で保持するかを決定し、暗黙に丸めない。元の情報は変更しない元ファイルから再取得できる。

座標は桁数を固定しないnumericで保存する。DMS有理数からの変換精度は実装時に決める。元EXIFの有理数まで完全に保持する正は元ファイルであり、DBの十進座標を原情報の代替にしない。緯度・経度は両方有効な場合だけ保存する。

## 認証と利用者

app_usersは許可ID対応の提案で、行の存在だけでは認証にならない。信頼する入口で本人を識別し、登録済みの許可IDと照合する。安定IDの出所・管理方式は認証設計で確定する。表示名や未検証ヘッダーでは照合しない。

2人上限はDBの行単位CHECKでは保証できないため、運用登録・アプリ側検証で保証する。セルフ登録API・パスワード・役割テーブルは設けない。uploaded_byは追加者の記録であり、閲覧・削除の制限に使用しない。利用者削除で写真を連鎖削除しない。

## 保存と解析の整合性

1. 認証・認可・CSRF・ファイル検証を実施する。
2. サーバー発行キーの元に元ファイルを永続保存し、バイト数とSHA-256を検証する。
3. photosと、pending状態のmetadata・thumbnail行を同じDBトランザクションで登録する。
4. 元ファイルとDBの保存完了後だけ201を返す。写真本体の不正はメタデータ解析失敗と区別して拒否する。
5. 日時・GPSを個別に解析し、成功・情報なし・解析失敗を記録する。解析中も保存済み写真を一覧取得できる。サムネイルのready更新はメタデータ除去済みファイルの保存後に行う。

子行のFKとPKだけでは「親ごとに子が必ず存在する」ことは保証できない。同一トランザクションでの作成をアプリの責務とし、実装時の結合テストで検証する。解析は再実行可能とし、pendingとfailedを再処理できるようにする。失敗理由を記録する場合は固定コードを使い、EXIFや個人情報をログに残さない。

ファイル保存とDB更新は単一トランザクションにできない。DB登録失敗時に残った未参照ファイルは回収対象とするが、実行中アップロードと区別する猶予・照合方式を実装時に決める。DB参照のある元ファイルを回収しない。応答喪失後の再送は現APIどおり重複する可能性があり、ハッシュ一致だけで利用者の写真を統合しない。

## 一覧・将来の検索

初期一覧はdeleted_atがNULLの行をcreated_at DESC, id DESCで取得する。複合B-tree索引は逆順走査でき、同時刻の順序も確定する。カーソルは最後の(created_at, id)を基点にし、OFFSETで全件を走査しない。削除後はすべての取得経路で非表示を確認する。

撮影日時・座標は初期のPhotoレスポンスに含めない。将来の日・月分類は撮影現地日付を基準にし、日時不明なら追加日時を代用した旨を区別する。検索条件・撮影日時索引・地理索引は検索APIと実行計画に合わせて追加する。現在は空のアルバム等や未使用の検索索引を先回りで作らない。

## 削除

deleted_atはAPIで参照停止を表現する技術上の案であり、復元APIや保存期間を約束しない。元ファイル・子行の物理削除、バックアップの期限、ゴミ箱は未決。自動パージ・CASCADEは導入せず、保持方針承認後に物理削除の手順を設計する。単なる論理フラグを本番の保持方針決定の代用にしない。

## dbdiagram.ioでのレビュー

1. https://dbdiagram.io/d を開く。
2. 新しい図のエディタへ `db/schema.dbml` の内容を貼り付ける。
3. 4テーブル、利用者から写真への1対多、写真から2つの子テーブルへの1対1を確認する。
4. カラムのNoteとCHECK・索引を確認する。制約の正はDBMLのテキストとし、図だけで保証されたとは扱わない。

dbdiagram.ioへはスキーマ定義のみを渡し、実在利用者・写真・座標・資格情報を入力しない。リポジトリのDBMLを唯一の編集元とし、図側で変更した場合は必ずDBMLへ戻してPRでレビューする。

## ローカル検証

Node.jsとnpmが利用できる環境で、固定したCLIを一時領域へ導入する。

```sh
npm install --prefix work/dbml-tools --cache work/npm-cache --no-audit --no-fund @dbml/cli@12.0.0
work/dbml-tools/node_modules/.bin/dbml2sql db/schema.dbml --postgres -o work/schema-review.sql
git diff --check
```

SQLはDBML構文・型・関連の検証用の一時生成物で、マイグレーションとして適用しない。生成SQLとwork配下はコミットしない。実DBでの制約テスト、保存・削除・再起動の結合テスト、検索性能はDB製品選定・実装後に実施する。
