## 実装

DELETE `/api/albums`にJSONの`name`を渡す。既存の認証・Origin・X-Photo-Request検証を通し、名前はtrim・正規化しない。未知フィールド・不正JSON・不正型・0文字／100文字超・DBで表現不能なNULを拒否する。

アルバム行を`FOR UPDATE`で取得してから、そのアルバムの所属を全件削除し、最後にアルバム行を削除する。同一トランザクションで確定し、途中失敗では全件取り消す。不在は変更せず204。写真行・画像ファイル・メタデータ・お気に入り・ゴミ箱状態・他所属は変更しない。

既存の個別所属編集・一括追加は同じアルバム行に`FOR KEY SHARE`を取得するため、先行する編集の確定後に所属を削除できる。削除が先なら編集は404となり暗黙再作成しない。削除側は写真行を取得せず、「写真→アルバム」の既存ロック順との循環待ちを作らない。同名再作成は空のアルバムとなり、結果不明時の自動再削除は承認済みUIで避ける。

### 削除APIの結合テスト

1. 通常／ゴミ箱内の写真、他所属、空アルバムを含む削除。不在の204、元画像・JPEGのバイト一致、全写真行の一致、別接続での再取得、同名再作成で所属なし。
2. 前後空白・空白だけ・日本語・スラッシュ・ドット・URL特殊文字・絵文字100文字の完全一致、未知名の204。
3. 不正JSON・型・未知フィールド・0／101文字・NUL、未認証401・第三者／Funnel／Origin／カスタムヘッダー不備403で変更なし。
4. アルバム行削除時のテスト専用トリガーで障害を発生させ、先に削除した所属も戻ること、内部診断を応答に露出しないこと。
5. 先行所属編集のKEY SHARE待ちと、その確定済み所属の削除。
6. 削除ロックで待つ個別追加／解除／一括追加が削除確定後404となり、所属やアルバムを暗黙再作成しないこと。
7. 同時削除の204、削除中の同名作成の待ち、再作成したアルバムに所属なし。
8. 実APIの個別追加／解除／一括追加／ゴミ箱／復元と削除を並行実行し、写真と残るアルバムの所属を保持し、500やデッドロックにならないこと。
