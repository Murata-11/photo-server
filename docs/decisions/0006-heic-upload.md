# ADR 0006：48MP・HEICアップロード（提案）

- 対象：Issue #20。2026-11-11の「Issue20をreadyにしたい」に基づく仕様具体化。
- 状態：提案。対象コミットのPO承認・仕様PRのマージは未実施。実装・本番反映の承認とは扱わない。

## 形式と保存

JPEG/PNG/WebPにHEVC符号化のHEIC静止画を追加し、全形式で50MiB・60,000,000画素以下（境界を含む）を受け付ける。8064×6048は48,771,072画素で範囲内。ブラウザーのMIMEはimage/heic・image/heifを許可するが、AVIFや他コーデックのHEIFを含めない。MIMEが空・別形式の場合は案内して拒否し、拡張子だけで受け付けない。iOSで別MIMEが必要と判明した場合は、対象と検証方法を示して仕様を再確認する。

HEIFの独立した主画像は1枚に限定する。独立画像が複数、画像シーケンス、動画は拒否する。主画像のタイル・サムネイル・補助画像は独立写真と数えず、代表画像だけを表示する。Live Photosの動画部分、HDR表示の再現、RAW/ProRAW、AVIFは対象外。HEIC内の回転・反転とEXIF orientationを二重適用せず、表示用JPEGはsRGB・長辺1600px以内・品質85、EXIF/GPSを除去する。元画像は変更せず保存し、元MIME・元ファイル名とバイト列をダウンロードする。既存の認証・非公開保存・EXIF抽出方針は維持する。DB移行・既存元画像の変換は不要。

## デコーダーの構成案

既存のsharp 0.35.5を維持し、DockerのネイティブlibvipsにlibheifとHEVCデコーダーlibde265を組み込む。MIME許可だけの追加や、JPEGへのブラウザー内変換は採用しない。npm配布のsharpバイナリにHEVCデコードがあると仮定しない。

ビルド候補はlibvips 8.18.7 / libheif 1.23.7 / libde265 1.0.19。調査時に各公式タグの存在と、sharpの必要libvipsが8.18.7以上であることを確認した。これらの組合せのビルド・HEIC処理はまだ未検証。実装PRで公式ソースの固定タグ・コミット・チェックサム、コンパイラー／ビルドツールを記録し、HEVCデコードのみ有効にする。不要なHEVCエンコーダーを追加しない。ランタイムに必要な共有ライブラリとライセンス表示を含める。OS／ネイティブライブラリの脆弱性も確認する。

sharpはこのlibvipsへリンクしてビルドする。ビルド時と実行時の両方でHEVCフィクスチャのデコードを確認し、共有ライブラリ不足やプリビルド版への意図しない置換を検出する。HEIFの独立画像数・コーデック・シーケンスの判定はlibheifの情報に基づく。sharpのpagesだけで上記の区別を保証できない場合はlibheifの検査用ヘルパーを使い、シェル文字列に入力ファイル名を渡さない。補助画像を含むiPhone相当のフィクスチャを含め、誤受理・誤拒否の両方を検証する。

Windowsも既存のDocker Desktop/Linuxコンテナを正式な実行経路とする。ホスト上でのNode直接起動はカスタムlibvipsを用意した開発環境に限る。外部変換サービス、認証・公開範囲、課金リソースは追加しない。

## リソースと失敗処理の案

60MPは提案上限であり、安全性の実測結果ではない。60MPのRGBA生データ1面だけで約240MBを要し、HEICの補助画像・中間バッファー・同時処理で増える。1プロセスの画像処理を1件に直列化し、待機は2件まで、処理枠取得後のデコードは30秒で打ち切る案とする。単なるPromiseのタイムアウトではネイティブ処理が止まらないため、画像処理は終了可能な子プロセスで行う。上限超過・タイムアウト後の子プロセス回収・一時ファイル削除と次の正常処理を確認する。待機枠満杯・処理時間超過・デコーダー障害は503で通知し、破損とは区別する。

画像サイズ・画素数の安全上限とlibheif側の安全制限を無効化しない。幅×高さを展開前に確認し、宣言寸法と実デコードの両方で制限する。タイル・補助画像等による総メモリ増加も実測する。ファイル保存・DB登録へ進むのは画像検証とJPEG生成が成功した後。既存の保存・DB応答喪失時の孤立ファイル保持方針は変更しない。

本番相当のLinux Dockerにメモリ上限1GiB・CPU 2を与え、48MP JPEG/HEICと60MP境界をそれぞれ繰り返し測定する。コールド／ウォームの処理時間、コンテナ全体のピークメモリ、終了コード、OOM有無、3件までの同時要求、待機超過を記録する。48MP正常画像は30秒以内に成功し、OOMせず次の要求も処理できることを実装PRの基準とする。この予算で60MPが安定しない場合、上限や実行資源を黙って変更せず、結果と変更案をPOへ提示する。

## 検証と復旧

AIが実装PR作成前に、専用PostgreSQLと合成／再配布可能なフィクスチャで実APIを検証する。60,000,000画素（10000×6000）成功、60,000,001画素以上失敗、50MiB境界、48MP JPEG/HEIC、8/10-bit HEIC、回転・反転、補助画像、偽装・破損・独立複数画像・シーケンス・動画、既存形式、SHA-256一致、再起動保持、認証・CSRF、メタデータ除去、処理失敗後の回復を含む。HEIC素材には出典・許諾と作成方法を記録し、本番写真は使用しない。

POがマージ／リリース前に許諾した48MPのiPhone実機素材で、Windows Docker Desktop・Tailscale・Safariの選択から保存・閲覧・元画像取得まで確認する案とする。AIのDraft PR作成の前提にはせず、未実施を明示する。この分担も仕様承認の対象。

本番適用は別承認。従来どおり書き込みを停止し、コード・設定・DB・写真の整合バックアップを取る。DB構造は変えないが、HEIC追加後に旧版へ戻すと旧版は追加済みHEICを新規処理できない。既存JPEG表示／元バイト配信の互換性を隔離環境で確認し、HEICファイルを削除しない。DB・写真をバックアップへ復元する場合は取得後の変更を失うため別途承認する。

## 根拠

- sharp 0.35.5のnpmメタデータ：`config.libvips: >=8.18.7`。パッケージ内`dist/libvips.cjs`のカスタムlibvips検出も確認。
- <https://github.com/libvips/libvips/tree/v8.18.7> のmeson.build：libheif連携と安全制限の検出。
- <https://github.com/strukturag/libheif/tree/v1.23.7>：HEVCはlibde265でデコードする構成。
- <https://github.com/strukturag/libde265/tree/v1.0.19>。

ローカルのnpm標準バイナリはlibvips 8.18.7・libheif 1.23.5を含むが、`sharp.format.heif.input.fileSuffix`は`.avif`のみでlibde265もバージョン一覧にない。HEIFローダーがあることをHEVCデコード対応の根拠にしない。

タグの存在・ソースの確認を、Dockerのビルド成功・実デコード成功・安全性の実測と取り違えない。
