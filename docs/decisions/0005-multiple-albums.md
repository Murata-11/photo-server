# ADR 0005：写真の複数アルバム所属

- 状態：仕様レビュー中（対象コミットの承認・マージ前）
- 対象：Issue #21
- 方針合意：2026-11-11、POのチャット「いいですね。進めてください。」。仕様PR作成を進める。実装・マージ・本番適用は未承認。

## データモデル

既存の名前主キー `albums.name` を維持し、中間テーブル `photo_albums` に `photo_id uuid NOT NULL REFERENCES photos(id)` と `album_name text NOT NULL REFERENCES albums(name)` を置く。主キーは両列、アルバム起点の参照用に `(album_name, photo_id)` 索引を置く。現行にアルバム改名・削除・写真完全削除はなく、CASCADEは導入しない。図・DDLは後続実装時に更新する。写真ファイル・メタデータ・共有権限は変えない。

所属ごとのINSERT（ON CONFLICT DO NOTHING）とDELETEを使い、全所属の置き換えを行わない。対象の写真とアルバムは存在確認し、未所属の解除も存在する両対象に限り成功させる。追加・解除は同じ写真行のロックをトランザクション内で取得し、同一所属の競合を直列化する。別所属は直列実行されても情報を失わない。写真応答は重複なしの所属名配列をDBの名前順で返す。一覧の写真順は現行の created_at DESC, id DESC を維持する。

## API互換性と画面

HTTP契約は `api/openapi.yaml`、業務ルールは `docs/product.md` 第10節を正とする。旧単一所属フィールドを削除するため破壊的な変更となる。公開された外部クライアントは想定せず、バックエンド・フロントエンドを同時更新する。旧フロントのタブは更新後に再読み込みする。旧PATCHのalbumを黙って受け付けず400にする。

生成クライアントは本文なし204を扱う。チェック変更で対象の1所属だけを即時追加・解除する。保存中はその行だけを無効化し、行ごとの重複送信を防ぐ。異なる行は並行操作を許す。成功した行は保持し、失敗・応答喪失は操作前の状態へ戻して対象操作の再試行を表示する。冪等なAPIで応答喪失後も安全に再試行する。

同時保存時の古い一覧応答で他の所属を上書きしないよう、操作世代を管理し、処理中の行がなく最新世代の場合のみ再取得結果を親画面へ反映する。再取得のみ失敗した場合は更新を再送せず再取得する。パネルを閉じても開始済みの操作と再取得は継続し、閉じた後に失敗したら通知する。パネルを再度開いた場合の取得順序・未完了操作は後続実装でも検証する。

2026-11-11、POの「この案でPRを更新して」に基づき、ツールバーのアルバムアイコンとチェック即時保存へ更新。所属編集の入口をアイコンに統一し、情報パネルには要約のみ表示する。PCのアイコン付近のパネル／スマートフォンの下部パネル、最大高さと行内の保存状態はStorybookを正とする。APIの個別操作契約とDB設計は維持する。アルバム自体を管理する画面は別Issueとする。

仕様PRの共有App変更は通常画面にも及ぶが、実APIは旧契約のまま。仕様PRのマージだけでデプロイしない。実装PRで契約適合を完了してからリリースする。

## バージョン付きDB移行

後続実装で現行の初期DDL実行を履歴付き移行へ置き換える。専用の接続とDB advisory lockで移行を排他し、バージョン・適用時刻を記録する。新規DBと既存の履歴なしDBの両方を扱う。履歴なし既存DBの構造を検証し、想定外なら自動修復せず停止する。

中間テーブル作成、全photosの非NULL albumのコピー（deletedを条件にしない）、旧所属との件数・ペア一致検証、旧album列の削除、履歴の登録を同じトランザクションで実行する。空文字など想定外の旧データは黙って捨てず失敗させる。albums行は削除せず、NULLは未所属のまま維持する。移行済みなら再適用しない。失敗時は全体をロールバックし、アプリは起動せず非0終了する。写真ファイルは触らない。

## 適用と復旧

本番反映は別途PO承認が必要。アプリを停止して書き込みを止め、旧コミット・設定とDBのpg_dump・写真ディレクトリを一組で保存する。旧アプリを停止したまま新アプリで移行する。成功後に起動・所属・元画像・ゴミ箱と復元を確認する。

失敗時は新アプリを停止し、旧版のコードと移行前DBを専用の復元先へ戻す。写真ディレクトリも対応するバックアップを使う。複数所属を単一所属へ自動縮退するdown migrationは作らない。移行後に書き込みを再開した場合、バックアップへの復帰はその後の変更を失うため、対象と影響を示してPO承認を得る。検証成功までは旧バックアップを削除しない。
