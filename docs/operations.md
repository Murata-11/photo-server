# 運用手順

状態：運用設計の草案。アプリ、本番環境、CI/CD、バックアップは未構築であり、以下の実運用手順は未検証。実行可能なコマンドは実装後に追記する。

## 本番開始の条件

- 配置先、予算、構成、対応バージョンをPOが承認する。
- 製品仕様の受け入れ条件を検証する。
- 2人の認証成功と、未許可ユーザー・直接接続の拒否を確認する。
- 永続領域、容量制限、秘密情報の保管場所を確定する。
- RPO、RTO、バックアップ頻度・保持期間・保存先・復旧用鍵の管理者を決める。
- バックアップから隔離環境へ実際に復元し、DB・元画像の整合性と所要時間を確認する。
- 起動、停止、更新、復旧のコマンドと実行ディレクトリを本書に記載し、検証結果を残す。

## リリース手順案

1. 対象コミット、CI結果、変更内容、DB移行の有無と復旧方法を確認する。
2. POから対象バージョンの本番反映承認を得る。
3. 現行バージョンと設定を記録し、必要な整合バックアップを取得する。
4. 固定したバージョンの成果物で更新する。可変のlatestタグだけに依存しない。
5. 認証、一覧、テスト用写真の追加・表示・ダウンロードを確認する。本番写真を検証のために削除しない。
6. 結果、実施日時、実施者、対象コミットをリリース記録に残す。

失敗した場合は更新を止め、影響を報告する。DBの互換性がある場合だけ以前のアプリへ戻す。DB復元や本番データの変更は、影響と失われる更新を示してPO承認を得る。

## バックアップと復元

- 元画像とDBを整合する時点で取得する。停止・スナップショット・DBのバックアップ機能から採用方式を決める。
- 本体故障に備えて別の保存先に暗号化して保持し、復号鍵をバックアップ本体だけに保存しない。
- 保持世代、削除済み写真の残存期間、完全削除の扱いを製品仕様と整合させる。
- 復元テストは隔離環境で行い、本番データへの上書きを避ける。個人情報を扱う場合はPO承認を得る。
- 復元後にDB参照、元画像の一致、認証、必要な派生データの再生成を確認する。
- バックアップ成功時刻、復元テスト結果、保管先、鍵の参照方法を安全な運用記録に残す。秘密値は記載しない。

## 日常監視

導入時に通知先としきい値を決め、通知テストも実施する。

- アプリの応答とエラー率
- ディスク空き容量、保存失敗
- バックアップの最終成功時刻と失敗
- サーバーとTailscaleの接続状態
- 依存関係・OSのセキュリティ更新

ログには元画像、秘密値、不要な個人情報を出さない。ログ保持期間と閲覧権限も定める。

## 障害対応

1. 発生時刻、症状、影響範囲を記録し、ログと直前の変更を確認する。
2. データ損失や公開範囲の拡大を伴う操作はPO承認前に行わない。
3. 原因と復旧案を示し、承認が必要な操作を区別する。
4. 復旧後、写真とDBの整合性・認証・基本操作を確認する。
5. 再発防止をIssueにし、手順を更新する。

## 初期実装のローカル運用（ADR 0003）

起動・停止はREADMEに従う。写真とDBは別の永続領域であり、コンテナ再作成だけでは削除しない。バックアップ前にはアプリを停止して書き込みを止め、PostgreSQLの`pg_dump`とPHOTO_DATA_DIRの全ファイルを一組として取得する。復元は空の専用DBと専用ディレクトリへ行い、元ファイルのSHA-256と一覧・元画像・ゴミ箱状態を照合する。稼働中のPGデータディレクトリを単純コピーしない。バックアップ保存先・暗号鍵・保持期間・実際の復元訓練は本番投入前に決定する。

保存失敗・DB応答喪失・プロセス停止時には孤立ファイルが残り得る。DBの写真UUIDと写真ディレクトリの`.original` / `.jpg`を照合し、容量を監視する。応答が失われてもDB登録済みの場合があるため、失敗ファイルを自動削除しない。手動の削除や本番データへの操作には別途承認が必要。

ゴミ箱の保持期限・完全削除・バックアップ消去は実装していない。本番Tailscale設定・実際の2人の端末認証・第三者の拒否・再起動・バックアップ復元を確認するまでは本番受け入れ完了と扱わない。
