# 仕様管理：StorybookとOpenAPI

## 採用方針と現在の状態

POとの合意に基づき、画面仕様にはStorybook、API契約にはOpenAPIを採用する。本書は運用と配置を定めるもので、画面やAPIの仕様自体を重複記載しない。

OpenAPIの初期レビュー案を `api/openapi.yaml` に配置した（未承認・未実装）。Storybook、生成ツール、CIは未導入。アプリの技術選定も未完了であり、契約テストや生成物の整合性チェックは未実行。定義だけを完成した実装と扱わない。

## 唯一の正と配置

| 対象 | 正となる場所 | 記載内容 |
| --- | --- | --- |
| 製品仕様 | `docs/product.md` | 目的、業務ルール、受け入れ条件、画面間の業務フロー |
| UI仕様 | `src/**/*.stories.tsx`（配置予定） | 実際のコンポーネントを使う画面・部品の表示と操作状態 |
| Storybook設定 | `.storybook/`（配置予定） | 実行・ビルドの設定。仕様本体はStory |
| API契約 | `api/openapi.yaml`（レビュー案） | パス、操作、入力、応答、エラー、認証要求 |
| 内部設計 | `docs/architecture.md`、`docs/decisions/` | 構成、認証方式、保存方式、選定理由 |

Storyの拡張子はTypeScript/JSX採用を想定した配置案であり、フレームワークの採用を意味しない。技術選定時に実際の配置を確定し、この表を同じPRで更新する。

仕様間に矛盾があれば、製品目的と関連する仕様を照合してPOに確認する。実装を既成事実として仕様を変更しない。

## Storybookの作成基準

- アプリで使用するコンポーネントと共有し、レビュー専用の別実装にしない。
- 対象画面と部品に安定したStory名を付け、Issueの受け入れ条件と関連付ける。
- 通常、読み込み中、空、失敗、権限エラー、削除確認など、対象機能に必要な状態を用意する。
- 必要な操作をinteraction testで検証し、キーボード操作やアクセシビリティも確認する。
- APIを模擬する場合はOpenAPIから生成した契約・型に従う。手書きのシナリオ値も契約に照らして検証する。
- 実在する個人写真や本番の秘密情報を使わない。
- 一連の画面遷移や実際の認証・保存は、業務フローとE2E・結合テストで別途確認する。

## OpenAPIの作成基準

- OpenAPI 3.1系を基本とし、具体バージョンとツール対応を導入時に確認・固定する。
- API契約を先に編集し、サーバーコードから生成した別の仕様を並行管理しない。
- operationId、入力制約、content type、成功・エラー応答、セキュリティ要件を明示する。
- 写真のアップロード・バイナリ取得、ページングなどは採用する振る舞いを承認してから定義する。
- 認証方式は内部設計と整合させる。利用者が任意指定できるヘッダーを認証手段として扱わない。
- 型・クライアント・モックの生成は固定したツールと再現可能なコマンドを使う。
- 生成物をコミットするかはツール選定時に決定する。コミットする場合は再生成後の差分がないことをCIで確認する。しない場合はビルド前に生成する。
- サーバーの実際の入力・応答を契約テストで確認する。認可、CSRF、永続性、バイナリ内容の一致などは別のテストも実施する。

## 変更と承認

1. Issueで目的と受け入れ条件を整理する。
2. AIがStorybook・OpenAPIの必要な変更を作り、変更対象とレビュー方法を提示する。
3. POが対象コミットの仕様を承認する。設計PRを分けるか、同じPR内で承認後に実装を続けてもよい。
4. AIが実装と生成物を更新する。承認後の仕様変更は、その部分を再承認する。
5. 検証結果と仕様への対応をPRに記録し、マージ承認を受ける。

既存仕様に合わせるバグ修正は、新しい仕様承認を要しない。表示を変える変更は、単なるリファクタリングとして承認を省略しない。

## 導入時に用意する検証

- Storybook：静的ビルド、必要な操作テスト、アクセシビリティ確認。
- OpenAPI：構文・参照・規約の検証、mainとの差分による破壊的変更の検出。
- 生成物：型チェック、再生成による整合性確認。
- 実装：API契約テスト、認可・保存の結合テスト、主要業務フローのE2E。

破壊的なAPI変更には影響範囲と移行方針を示し、PO承認を必須とする。チェックを無効化して通過させない。

導入PRでは、ローカルとCIで使う正確なコマンド、ツールの固定バージョン、レビュー手順をREADMEに追記し、実行結果を残す。文書で方針を定めただけでは、実装との整合性が検証済みとは扱わない。
