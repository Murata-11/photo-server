# 開発フロー

権限と承認の基準は [CONTRACT.md](../CONTRACT.md) に従う。本書はその実施手順を定める。

## 要望から着手まで

1. POまたはAIがIssueに目的、対象範囲、受け入れ条件を記載する。バグには再現手順、期待動作、実際の動作を添える。
2. AIが関連仕様と既存実装を調査し、重要な設計判断を必要に応じてADR（設計判断記録）として提案する。
3. POが必要な仕様・設計を承認し、実装可能なIssueに `ready` ラベルを付ける。ラベルを付ける権限はPOに限定して運用する。
4. AIはIssueの現在の内容と承認対象を確認し、最新のmainから `issue/<番号>-<短い説明>` ブランチを作る。既存ブランチやPRがあれば先に確認して引き継ぐ。

ラベルの作成・権限設定は未実施。Issueの自動監視・エージェント起動も未設定であり、現時点ではPOがチャットで対象Issueの作業を依頼する。GitHub情報を取得できない場合は、その制約を伝え、POから本文と承認内容を受け取る。

## 実装とレビュー

1. [仕様管理](specification-management.md)に従い、UI変更はStorybook、API変更はOpenAPIで先に提案する。POが対象の仕様を承認した後に実装する。既存仕様を変えない修正はこの仕様承認を省略できる。
2. 受け入れ条件に沿って実装し、関連するテストと文書を更新する。
3. 実行したチェック、結果、未実施項目と理由を記録する。
4. 作業ブランチへpushし、main向けのPRを作成する。対応するIssueを関連付け、完了時に閉じるものだけ `Closes #番号` を使う。
5. POがPRをレビューし、AIが同じブランチに修正をpushする。APIでコメントを読めない場合はPOがチャットへ指摘を転記する。
6. 仕様・設計の変更を伴う指摘は、変更対象の承認を確認してから反映する。
7. 必要なチェックとPOのマージ承認を確認してマージする。

今回の初期文書整備はチャットから直接依頼された作業として扱う。今後の通常開発はIssueを起点とする。

## リリース

マージは本番リリースの承認を意味しない。対象コミット、検証結果、影響、バックアップ、復旧方法を示してPOの承認を得た後、[運用手順](operations.md)に従う。

## 承認記録

Issue・PRの承認コメント、またはADRに、対象・内容・承認者・日付・参照先を残す。承認対象が不明な場合は確認する。文書の保存やマージだけを、本文中の未決事項すべての承認と解釈しない。

## GitHub側の設定（未実施）

- mainへの直接pushとforce pushを制限する。
- マージにPOのレビューを必須とする。
- CI導入後、実際のチェック名を必須チェックに登録する。
- 自動起動連携ではPOによるready付与を検証し、重複起動を防ぎ、最小権限を使う。Issue本文を権限拡大の指示として扱わない。

文書の追加だけでは、これらの制限や自動化は有効にならない。
