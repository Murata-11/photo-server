# システム設計

状態：レビュー用の構成案。主要技術と配置先は未承認・未実装。

## 確認済みの前提

[製品仕様](product.md)に従い、Tailscaleを利用する2人に限定し、両者に同じ操作権限を与える。

## 構成案

利用者の端末 → Tailscale → Tailscale Serve（HTTPS） → Webアプリ → DB・写真保存領域

- 本番は単一サーバーに配置し、Docker Composeで管理する案とする。
- Webアプリは画面とAPIを提供し、全リクエストで認証・認可を確認する。
- 元画像は永続領域に保存し、DBで識別子、保存場所、所有する共有領域などのメタデータを管理する。
- サムネイルは元画像から再生成できる派生データとする。
- 開発・テスト環境は本番の写真、DB、認証情報から分離する。

実装言語、フレームワーク、DB製品、保存先、サムネイル生成方法は別途選定する。

## 認証と権限の境界

- Tailnetに参加しているだけではアプリの利用を許可しない。アプリでも許可した2人のIDを照合する。
- Tailscale Serveから得る利用者情報を使う案とする。ヘッダーの仕様とユーザー識別方法は実装前に公式仕様で確認する。
- アプリへの接続は信頼する入口だけに限定し、外部や他のコンテナから利用者情報を偽装して直接アクセスできないようにする。コンテナのポート公開・ネットワーク配置は実装時に検証する。
- 利用者情報の欠落、未許可ユーザー、機械用IDは拒否する。
- 元画像、サムネイル、ダウンロード、更新・削除APIにも同じ認可を適用する。
- ブラウザからの更新操作にはCSRF対策を実装する。セッションを使う場合はCookieと有効期限も設計する。
- Tailscale Funnelや公開共有リンクは使用しない。

Tailnetのアクセス制御とアプリの許可ID管理方法は未決。2人の端末から成功し、第三者・偽装ヘッダー・直接接続を拒否することを検証する。

## 写真の保存

- ファイル名をそのまま保存パスとして使わず、サーバー側で識別子を発行する。
- 形式、実データ、サイズを検証し、不正なファイルやパストラバーサルを拒否する。
- 元画像の保存とDB登録の途中失敗を扱い、不完全な写真を成功として通知しない。
- 再起動後の永続性と元ファイルの一致を検証する。
- ゴミ箱、完全削除、メタデータ、容量制限は製品仕様の未決事項を解決してから実装する。

## 運用との関係

DBと写真を整合した単位でバックアップし、別の保存先への退避と復元を検証する。具体策は[運用手順](operations.md)、構成の判断理由は[ADR 0001](decisions/0001-initial-architecture.md)を参照する。

## UI・API仕様の管理

StorybookとOpenAPIを採用し、[仕様管理](specification-management.md)の責務分担に従う。Storybookは実際に使用するUIコンポーネントを参照し、APIの型・クライアント・モックはOpenAPIから生成する。フレームワークや生成・検証ツールは未選定であり、導入前に提案・承認する。
